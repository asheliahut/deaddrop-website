## stdout is for tickets

`serve` and `reset` print each ticket on **stdout** as one line, and
everything else (progress, status, connection paths, warnings) goes to
**stderr**:

| Mode | stdout line |
| --- | --- |
| default | `<ticket>` |
| `--encrypt` | `<ticket> <key>` |
| `--encrypt --hide-key` | `<ticket>` |

So this works in every mode:

```sh
deaddrop serve x.torrent > tickets.txt &
# ...later
read -r TICKET KEY < tickets.txt     # KEY is empty without --encrypt, or with --hide-key
```

After a [reset](/docs/guides/resetting/), the server prints the new ticket
(and key) as another line. `deaddrop reset` prints the same line, so you can
capture it directly:

```sh
read -r TICKET KEY < <(deaddrop reset "$TICKET" 'magnet:?xt=...')
```

`fetch` accepts an empty key, so passing it along unconditionally is fine:

```sh
DEADDROP_KEY="$KEY" deaddrop fetch "$TICKET" -o ./dl
```

<Aside type="note" title="Changed in 2.0">
	1.0 always printed `<ticket> <key>`. Scripts that require a non-empty `KEY`
	need `--encrypt` now. See [1.0 vs 2.0](/docs/whats-new/#stdout-format).
</Aside>

## Progress in scripts

Progress bars are only drawn when stderr is a terminal, so `2> log.txt`,
pipes and systemd already get plain progress lines with no escape codes. For
a recorded terminal (`script`, tmux logging, CI pseudo-terminals) add
`--no-progress`. See [Progress & logging](/docs/guides/progress/).

## Exit status

| Code | Meaning |
| --- | --- |
| `0` | Success, including a single-use server shutting down after its download, and Ctrl-C. |
| `1` | Error. |
| `2` | Bad command-line usage. |

## Help

`deaddrop --help` (or `deaddrop help <command>`) has the full reference:
examples, environment variables, config precedence and exit codes. `-h` gives
a shorter summary.
