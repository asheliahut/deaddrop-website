deaddrop moves data that people want kept private, so security reports are
taken seriously.

<Aside type="danger" title="Don't report in public">
	Please do not open a public issue, discussion or pull request for a security
	problem.
</Aside>

## Reporting a vulnerability

Report it privately through GitHub's private vulnerability reporting (the
**Security** tab → **Report a vulnerability**):

<LinkButton href="https://github.com/asheliahut/deaddrop/security/advisories/new" icon="external" variant="primary">
	Report a vulnerability
</LinkButton>

Please include, as far as you can:

- The deaddrop version (`deaddrop --version`) or commit, and your platform.
- Which command and options are involved (`serve`, `fetch`, `reset`,
  notifiers, config file).
- What an attacker needs (the ticket, the key, network position, a reset
  token, local access to the server, ...) and what they gain.
- Steps to reproduce, or a proof of concept.

Leave real tickets, keys, reset tokens and webhook URLs out of the report, or
rotate them first.

## Supported versions

deaddrop follows [semantic versioning](https://semver.org). Security fixes
land in the latest release of the current major version; there are no
backports to older minor or patch releases, so upgrade to the newest `2.x.y`
to pick up a fix.

| Version | Supported |
| --- | --- |
| Latest `2.x.y` (current major) | ✅ |
| Older `2.x.y` releases | ❌ (upgrade to the latest) |
| `1.x` and earlier | ❌ |
| `main` | ✅ (best effort) |

When a new major version ships, the previous major stops receiving fixes.
Installed with Homebrew? `brew upgrade deaddrop` picks up security releases.

## What to expect

deaddrop is maintained by volunteers, so these are goals rather than
guarantees:

- An acknowledgement within **7 days**.
- A first assessment (accepted, needs more info, or out of scope) within
  **14 days**.
- For accepted reports, a fix and a release as soon as practical, followed by
  a published GitHub security advisory. You'll be credited in the advisory
  unless you'd rather not be.

Please give us a reasonable chance to ship a fix before disclosing publicly.
If 90 days pass without a fix, or without an agreed timeline, you're free to
disclose.

## Scope

In scope are problems in deaddrop's own code that break what it promises. See
[Threat model → Promises](/docs/concepts/threat-model/#promises) for the list,
plus crashes or resource exhaustion that a remote peer can trigger cheaply.
For example:

- A relay or network observer reading the data; with `--encrypt`, recovering
  plaintext or names without the key; with `--hide-key`, the key showing up
  in any output or reset reply.
- A size probe being counted as a single-use download.
- `deaddrop skill` writing outside the chosen skills directory, or replacing
  or removing files it didn't write without `--force`.

Out of scope are the [known limits](/docs/concepts/threat-model/#known-limits)
(including that, without `--encrypt`, the ticket alone gives access to the
data), what an AI agent does with the instructions in the `deaddrop` skill,
and content legality, or what users choose to share.

Bugs in dependencies (iroh, iroh-blobs, librqbit, age/rage, ...) should go to
those projects. If deaddrop uses a dependency in a way that makes it
exploitable, or ships a version with a known advisory, report it here.

The canonical policy is
[SECURITY.md](https://github.com/asheliahut/deaddrop/blob/main/SECURITY.md) in
the repository.
